## 이번 실습의 목표
사용자의 이름과 나이를 저장하고 조회하는 웹 서비스를 만듭니다. 외부 요청은 ALB가 받고, 실제 프로그램은 비공개 EC2에서 실행합니다. 사용자 정보는 별도의 VPC 안에 있는 Aurora MySQL에 저장합니다. 비밀번호는 프로그램에 직접 적지 않고 Secrets Manager로 관리합니다.

## 자료를 사용하는 방법
처음에는 시간 제한 없이 순서대로 구축합니다. 두 번째에는 설정 이유를 설명하며 다시 구축하고, 마지막에는 공식 제한시간인 4시간에 맞춰 연습합니다. 이 자료의 시간 배분과 설정 예시는 학습용 제안이며, 공식 요구값과 구별해 표시했습니다.

## 시작 전 준비물
- AWS 실습 계정과 서울 리전(ap-northeast-2) 접근 권한
- SSH 또는 Session Manager로 접속 가능한 환경
- 실습 결과를 기록할 필기구
- 제공된 제1과제 mark.sh 및 실제 시행과제 원본

이 학습자료에는 바이너리 파일을 첨부하거나 별도로 준비할 필요가 없습니다. 콘솔에서 인프라를 구성하고 설정 결과를 확인하는 과정을 중심으로 학습합니다. API 확인은 애플리케이션이 실행 중인 실습 환경에서 활용하는 확장 활동입니다.

## 기준 자료
실제 시행과제 HWP와 제1과제 공식 채점기준 HWP를 기준으로 작성했습니다. 앞서 받은 요약 채점표의 skills-* 이름, 일반 MySQL 3306, 100점 예시는 이 시행과제에 적용하지 않습니다. 공식 제1과제는 50점입니다.

# 전체 구조를 먼저 이해하기

## 요청이 이동하는 길
인터넷 사용자 → 공개 ALB(80) → 비공개 앱 EC2(8080) → VPC Peering → 비공개 Aurora MySQL(3307)
앱 EC2 → Secrets Manager 인터페이스 엔드포인트(443) → DB 접속정보 읽기
앱 EC2 → NAT Gateway → 패키지 설치 등 외부 접속

## 세 가지 서브넷의 역할
- Public: 인터넷 게이트웨이 경로가 있습니다. ALB, Bastion, NAT Gateway를 배치합니다.
- App: 인터넷에서 직접 접속하지 않습니다. ALB 요청을 받고 NAT를 통해 외부로 나갑니다.
- DB: 인터넷 기본 경로를 만들지 않습니다. 앱 서브넷과 DB 접속에 필요한 통신만 허용합니다.

## 반드시 기억할 고정값
- 앱 VPC: worldpay-app-vpc / 10.0.0.0/16
- DB VPC: world-db-vpc / 10.100.0.0/16
- DB VPC 이름은 원문에서 world-db-vpc입니다. worldpay-db-vpc로 바꾸지 않습니다.
- 앱 실행 포트 8080 / ALB HTTP 80 / DB 3307
- EC2: Amazon Linux 2023, x86 계열, t3.micro
- ASG 최소 2대 / 평균 CPU 목표 70%

## 학습용 작업 순서와 4시간 연습 배분
0~15분: 이름·권한·리전 확인 → 15~65분: 네트워크 → 65~110분: DB·Secret → 110~165분: 앱·ALB → 165~195분: ASG → 195~220분: 로그·대시보드 → 220~240분: 검증·수정
DB 생성은 대기시간이 있으므로 네트워크 준비가 끝나면 먼저 시작합니다.

## 교사가 설명할 문장
“학교 정문이 ALB라면 앱은 업무를 처리하는 교무실이고, DB는 별도 보관실입니다. 학생은 보관실에 직접 들어가지 않고 반드시 정해진 입구와 처리 담당을 거칩니다.” 비유를 설명한 뒤 실제 이름 ALB·EC2·Aurora와 포트 80·8080·3307을 다시 짚어 줍니다.

## 콘솔에서 찾아갈 서비스
상단 검색창에 VPC를 입력하면 네트워크를 설정합니다. EC2에서는 인스턴스·보안 그룹·대상 그룹·로드 밸런서·Auto Scaling을 설정합니다. RDS는 DB, IAM은 역할, KMS는 암호화 키, Secrets Manager는 접속정보, CloudWatch는 로그와 지표를 관리합니다.
콘솔 언어와 업데이트에 따라 메뉴명이 다를 수 있습니다. 한글 메뉴가 다르면 괄호의 영문 이름과 서비스 검색을 이용합니다.

# 콘솔 실습 A | VPC·서브넷 입력칸 따라가기

## VPC 두 개 생성
1. 상단 검색 VPC → 내 VPC(Your VPCs) → VPC 생성(Create VPC).
2. 생성할 리소스는 VPC만(VPC only). Name 태그 worldpay-app-vpc, IPv4 CIDR 수동 입력 10.0.0.0/16. 생성합니다.
3. 동일하게 world-db-vpc와 10.100.0.0/16을 생성합니다. 이 이름은 worldpay-db-vpc가 아님을 다시 확인합니다.
4. 각 VPC 선택 → 작업(Actions) → VPC 설정 편집에서 DNS 확인과 DNS 호스트 이름을 확인합니다.

## 서브넷 1개를 먼저 정확히 생성
1. 서브넷(Subnets) → 서브넷 생성(Create subnet).
2. VPC ID에서 worldpay-app-vpc를 선택합니다.
3. 이름 worldpay-pub-subnet-a / 가용 영역 ap-northeast-2a / IPv4 서브넷 CIDR 10.0.0.0/24를 입력합니다.
4. 생성 후 상세 화면에서 VPC·AZ·CIDR을 대조합니다. 나머지 5개는 앞의 공식 서브넷 목록을 보며 같은 방식으로 만듭니다. DB 서브넷 생성 시 VPC 선택을 변경해야 합니다.

## 라우팅 테이블 생성과 연결은 별도 작업
라우팅 테이블(Route tables) → 생성 → 이름 worldpay-pub-rt와 앱 VPC 선택 → 생성합니다. 이후 서브넷 연결(Subnet associations) → 서브넷 연결 편집(Edit subnet associations) → Public a/c 체크 → 연결 저장(Save associations).
경로(Routes) → 경로 편집(Edit routes) → 경로 추가(Add route)에서 0.0.0.0/0, 대상 Internet Gateway와 본인 IGW ID를 선택합니다. IGW를 앱 VPC에 먼저 연결해야 합니다.

## 저장 후 확인
이름만 같은 테이블이 다른 VPC에 생성되지 않았는지 확인합니다. 연결 탭에 Public a/c 두 개가 나타나고 경로 탭에 local과 IGW 기본 경로가 있어야 합니다.

# 콘솔 실습 B | NAT·피어링·NACL

![목적지별 라우팅 흐름](worksheets/images/worldpay-routes.png)

## NAT와 앱 경로
VPC → NAT 게이트웨이 → NAT 게이트웨이 생성. Public 서브넷 선택, 연결 유형 Public, Elastic IP 할당 후 생성합니다. Available이 되면 App a/c 라우팅 테이블 각각의 기본 경로 대상을 NAT Gateway로 지정합니다.

## 피어링과 응답 경로
피어링 연결(Peering connections) → 생성 → 이름 worldpay-vpc-peering, 요청자 앱 VPC, 수락자 DB VPC → 생성. 작업 → 요청 수락 후 Active 확인. 작업의 DNS 설정에서 원격 VPC DNS 확인을 양방향으로 활성화합니다. App a/c 테이블의 DB CIDR과 DB 테이블의 앱 CIDR 경로를 각각 추가합니다.

## NACL의 적용 대상
네트워크 ACL → ACL 생성 → worldpay-db-nacl / DB VPC. 서브넷 연결 → 연결 편집에서 DB a/c만 체크합니다. 인바운드 규칙 편집과 아웃바운드 규칙 편집을 각각 열어 앞의 3307·임시 포트 규칙을 입력하고 저장합니다.
학생 설명: “길을 만드는 것은 라우팅, 그 길을 통과시킬지 판단하는 것은 방화벽입니다.”

# 그림으로 이해하기 | DB 방화벽 검사

![DB 요청과 응답의 포트 변화](worksheets/images/worldpay-nacl.png)

## 콘솔의 어떤 칸을 봐야 하나요?
DB NACL 인바운드 화면의 포트 범위에는 3307을 넣습니다. 소스에는 앱 a의 10.0.10.0/24와 앱 c의 10.0.11.0/24를 서로 다른 규칙으로 넣습니다. 아웃바운드 포트 범위에는 1024-65535, 목적지에는 같은 앱 CIDR을 넣습니다.
규칙 번호 100과 110은 예시입니다. 이미 더 작은 번호에 거부 규칙이 있으면 허용 규칙까지 도달하지 못할 수 있으므로 전체 규칙을 읽습니다.

## 학생에게 물어보기
“앱이 45000번을 골라 요청했다면 DB의 응답은 어디로 갈까요?” 학생이 3307이라고 답하면 그림의 화살표 출발지와 목적지를 반대로 읽도록 안내합니다. 정답은 앱의 45000번입니다.
“DB의 포트를 3307로 바꾸면 인터넷에 공개해도 될까요?” 포트 변경은 접근 통제를 대신하지 않습니다. 비공개 서브넷, SG, NACL은 그대로 필요합니다.

## 보안 그룹 콘솔
EC2 → 보안 그룹 → DB SG 선택 → 인바운드 규칙 편집 → 사용자 지정 TCP / 3307 / 소스 앱 CIDR 두 개. ALB SG는 HTTP 80, App SG는 사용자 지정 TCP 8080의 소스를 ALB SG로 선택합니다.
기록: DB NACL 연결 서브넷 ______ / App SG의 소스 ______

# 보안 그룹 1 | 방향과 입력칸부터 이해하기

## 기준은 항상 지금 선택한 리소스입니다
ALB를 선택했다면 사용자 → ALB는 인바운드, ALB → 앱은 아웃바운드입니다. 앱을 선택했다면 ALB → 앱은 인바운드, 앱 → DB는 아웃바운드입니다. 같은 화살표라도 어느 쪽에서 보느냐에 따라 방향이 달라집니다.
인바운드의 소스(Source)는 누가 요청하는지, 아웃바운드의 대상(Destination)은 어디로 요청하는지입니다. 포트에는 새 연결을 받는 서버의 서비스 포트를 입력합니다. 앱이 DB로 가면 3307이지 앱 포트 8080이 아닙니다.

## 보안 그룹 5개를 먼저 만듭니다
EC2 → 네트워크 및 보안 → 보안 그룹 → 보안 그룹 생성. 다음 이름은 수업용 예시이며 공식 고정 이름은 아닙니다. 설명(Description)을 입력하고 VPC를 지정합니다.
| 그룹 이름 예시 | 생성할 VPC | 연결할 리소스 |
| --- | --- | --- |
| worldpay-alb-sg | 앱 VPC | ALB |
| worldpay-app-sg | 앱 VPC | ASG 앱 EC2 |
| worldpay-db-sg | DB VPC | Aurora DB 인스턴스 |
| worldpay-endpoint-sg | 앱 VPC | Secrets Manager Endpoint |
| worldpay-bastion-sg | 앱 VPC | Bastion EC2 |
두 그룹을 서로 참조할 때는 먼저 빈 그룹을 모두 만들고 규칙을 추가하면 순환 참조 때문에 막히지 않습니다. DB SG는 반드시 DB VPC에 만듭니다.

## 기본 아웃바운드 규칙을 꼭 확인
새 그룹에는 보통 모든 트래픽 / 전체 대상 규칙이 있습니다. 아래 표는 이 기본 규칙을 제거하고 필요한 규칙으로 바꾸는 학습용 구성입니다. 표의 규칙을 추가해도 기본 전체 허용이 남아 있으면 제한한 것이 아닙니다. 여러 SG가 연결되면 허용 규칙은 합쳐지므로 다른 SG의 전체 허용도 확인합니다.
작업은 이 실습용 그룹에만 적용합니다. 이미 사용 중인 공유 그룹을 임의로 수정하지 않습니다.

# 보안 그룹 2 | ALB·앱 규칙 그대로 입력하기

## ALB SG: 사용자를 받고 앱 8080으로 보냅니다
worldpay-alb-sg 선택 → 인바운드 규칙 편집(Edit inbound rules) → 규칙 추가(Add rule). 아래 한 줄을 넣고 저장합니다. 이어 아웃바운드 규칙 편집에서 기본 전체 허용을 표의 규칙으로 교체합니다.
| 방향 | 유형 / 프로토콜 | 포트 | 소스 또는 대상 |
| --- | --- | --- | --- |
| 인바운드 | HTTP / TCP | 80 | 소스 0.0.0.0/0 |
| 아웃바운드 | 사용자 지정 TCP | 8080 | 대상 worldpay-app-sg |
이 과제는 HTTP 80을 사용합니다. 443 리스너를 만들지 않았다면 ALB 인바운드 443을 필수로 추가하지 않습니다. 상태 검사도 앱과 같은 8080을 사용하므로 이 규칙이 상태 검사 연결을 허용합니다.

## App SG: ALB 요청을 받고 DB·AWS 서비스에 연결
| 방향 | 유형 / 프로토콜 | 포트 | 소스 또는 대상 |
| --- | --- | --- | --- |
| 인바운드 | 사용자 지정 TCP | 8080 | 소스 worldpay-alb-sg |
| 아웃바운드 | 사용자 지정 TCP | 3307 | 대상 10.100.0.0/24 |
| 아웃바운드 | 사용자 지정 TCP | 3307 | 대상 10.100.1.0/24 |
| 아웃바운드 | HTTPS / TCP | 443 | 대상 0.0.0.0/0 |
| 아웃바운드 | HTTP / TCP | 80 | 대상 0.0.0.0/0 |
HTTP·HTTPS 외부 통신은 문제에서 허용한 80/443 아웃바운드 예시입니다. 443은 Secret, 로그, SSM 등 클라이언트 통신에 쓰이며 실제 접근에는 NAT 또는 해당 서비스 엔드포인트 경로도 있어야 합니다. DB CIDR은 두 DB 서브넷 모두 허용해 DB 위치 변경에도 대응합니다.

## 그룹을 선택하는 입력 방법
소스/대상 종류를 사용자 지정(Custom)으로 두고 값 입력칸에 실제 sg-... ID 또는 그룹 이름을 입력합니다. 검색 목록에 뜬 해당 보안 그룹을 클릭해 선택합니다. 문자열 worldpay-alb-sg를 CIDR 주소처럼 직접 확정하는 것이 아닙니다. 같은 이름이 여럿이면 ID와 VPC를 함께 비교합니다.

# 보안 그룹 3 | DB·엔드포인트의 응답은 자동 허용

## DB SG: 앱 서브넷에서 오는 3307만 받기
| 방향 | 유형 / 프로토콜 | 포트 | 소스 또는 대상 |
| --- | --- | --- | --- |
| 인바운드 | 사용자 지정 TCP | 3307 | 소스 10.0.10.0/24 |
| 인바운드 | 사용자 지정 TCP | 3307 | 소스 10.0.11.0/24 |
| 아웃바운드 | 이 앱 연결에 신규 규칙 없음 | - | 기본 전체 허용 제거 |
기본 MySQL/Aurora 유형을 고르면 3306이 자동 입력될 수 있습니다. 사용자 지정 TCP를 선택하고 3307을 직접 적습니다. 앱 서브넷만 허용하며 0.0.0.0/0으로 DB를 열지 않습니다. 같은 리전 피어링에서 SG 참조도 가능하지만, 이 학습지에서는 DB 구간을 CIDR로 통일합니다.
DB가 먼저 시작하는 추가 통신을 별도로 설계한다면 그 용도의 아웃바운드 규칙이 필요합니다. 위 구성은 앱이 시작한 DB 연결에 대한 예시입니다.

## Endpoint SG: 앱이 Secret을 읽는 HTTPS 받기
| 방향 | 유형 / 프로토콜 | 포트 | 소스 또는 대상 |
| --- | --- | --- | --- |
| 인바운드 | HTTPS / TCP | 443 | 소스 worldpay-app-sg |
| 아웃바운드 | 이 요청의 응답용 규칙 없음 | - | 기본 전체 허용 제거 |
Endpoint SG는 인터페이스 엔드포인트에 연결합니다. App SG가 아닙니다. 앱의 아웃바운드 443이 허용되어도 Endpoint SG의 인바운드 443이 막혀 있으면 연결이 실패합니다.

## “아웃바운드가 비어도 응답하나요?”
네. SG는 허용된 연결의 상태를 기억합니다. 앱이 DB에 연결할 때 App SG 아웃바운드 3307과 DB SG 인바운드 3307이 허용되면, 그 연결의 DB 응답은 자동 허용됩니다. DB SG 아웃바운드에 앱의 임시 포트를 별도로 적지 않습니다.
하지만 DB 서브넷의 NACL은 상태를 기억하지 않습니다. NACL 응답 임시 포트 허용은 앞의 별도 규칙대로 필요합니다. SG와 NACL 설정을 서로 복사하면 안 됩니다.

# 보안 그룹 4 | Bastion과 실제 리소스 연결

## Bastion은 접속 방식 하나를 먼저 정합니다
SSH 방식이라면 아래 예시를 사용합니다. 내 IP(My IP)는 현재 사용하는 인터넷 공인 IP의 /32입니다. 집·학교 네트워크를 옮겨 접속 IP가 바뀌면 갱신해야 합니다.
| 방향 | 유형 / 프로토콜 | 포트 | 소스 또는 대상 |
| --- | --- | --- | --- |
| 인바운드 | SSH / TCP | 22 | 소스 내 공인 IP/32 |
| 아웃바운드 | HTTP / TCP | 80 | 대상 0.0.0.0/0 |
| 아웃바운드 | HTTPS / TCP | 443 | 대상 0.0.0.0/0 |
Session Manager만 쓴다면 SSH 인바운드 22는 필요하지 않습니다. 443 아웃바운드, SSM용 역할·에이전트·서비스 경로가 필요합니다. 이 표는 Bastion→앱 SSH나 Bastion→DB 직접 접속을 추가하지 않은 구성입니다. DB 초기화는 앱 EC2의 Session Manager에서 수행합니다.

## 만든 SG를 리소스에 연결하는 화면
- ALB: EC2 → 로드 밸런서 → worldpay-alb → 보안(Security) → 보안 그룹 편집 → ALB SG 선택.
- 앱: EC2 → 시작 템플릿의 새 버전 → 네트워크 설정에 App SG 선택 → ASG가 새 버전을 사용하도록 설정. 기존 EC2는 네트워킹 → 보안 그룹 변경에서 별도로 확인합니다.
- DB: RDS → DB 인스턴스 선택 → 수정(Modify) → 연결의 VPC 보안 그룹에 DB SG 선택. 적용 시점과 현재 상태를 확인합니다.
- Endpoint: VPC → 엔드포인트 선택 → 작업 → 보안 그룹 관리에서 Endpoint SG 선택.
- Bastion: EC2 → 인스턴스 선택 → 작업 → 보안 → 보안 그룹 변경에서 Bastion SG 선택.

## 마지막 확인
리소스 상세의 실제 SG ID와 규칙을 대조합니다. 새 그룹을 만들기만 하고 기본 SG가 계속 연결된 상태를 피합니다. EC2에 여러 SG가 붙었다면 원치 않는 8080 전체 공개나 전체 아웃바운드 허용이 다른 그룹에 남아 있지 않은지 봅니다.

# 보안 그룹 5 | 한 요청을 양쪽에서 확인하기

## 예시 A: 사용자 → ALB → 앱
1. 사용자가 ALB의 HTTP 80으로 요청합니다. ALB SG의 인바운드 80 / 0.0.0.0/0이 허용합니다.
2. ALB가 새 연결로 앱의 8080에 요청합니다. ALB SG 아웃바운드 8080 / App SG와 App SG 인바운드 8080 / ALB SG가 모두 필요합니다.
3. 앱의 응답은 허용된 연결에 대한 응답이므로 별도의 App SG 아웃바운드 8080이나 ALB SG 인바운드 임시 포트를 만들지 않습니다.

## 예시 B: 앱 → DB
1. 앱이 DB의 3307로 새 연결을 시작합니다.
2. App SG 아웃바운드 3307 / DB 서브넷 CIDR을 확인합니다.
3. DB SG 인바운드 3307 / 앱 서브넷 CIDR을 확인합니다.
4. 응답용 SG 규칙은 추가하지 않습니다. 대신 라우팅과 DB NACL의 요청·응답 규칙을 따로 확인합니다.

## 예시 C: 앱 → Secrets Manager Endpoint
App SG 아웃바운드 443 / 0.0.0.0/0 규칙은 내부 Endpoint IP도 포함합니다. Private DNS와 경로가 정상이라면 내부 인터페이스로 갑니다. Endpoint SG 인바운드 443 / App SG를 확인하고, 마지막으로 IAM·KMS·Endpoint 정책을 확인합니다. SG를 열었다고 Secret 읽기 권한까지 생기지 않습니다.

## 교사가 칠판에 적을 세 질문
“누가 연결을 시작했나요? 받는 서비스의 포트는 몇 번인가요? 보내는 쪽 아웃바운드와 받는 쪽 인바운드를 모두 확인했나요?”
같은 SG를 참조한다고 규칙이 서로 복사되는 것은 아닙니다. App SG에서 ALB SG를 소스로 선택하는 것은 그 그룹에 연결된 리소스에서 오는 요청을 식별하는 것입니다.
외부 DNS 서버를 별도로 쓰지 않는 이 예시에서 AmazonProvidedDNS에 임의의 UDP 53 SG 규칙을 필수로 추가하지 않습니다. 사용자 정의 DNS 서버를 쓰면 그 서버용 통신을 별도로 설계합니다.

# 보안 그룹 6 | 흔한 실수와 학생 확인표

## 틀린 설정을 먼저 찾아봅시다
| 학생의 설정 또는 증상 | 확인·수정할 내용 |
| --- | --- |
| App 인바운드 8080의 소스가 0.0.0.0/0 | ALB SG로 변경 |
| ALB 아웃바운드가 80만 있음 | 앱 대상 포트 8080을 App SG로 허용 |
| DB에 MySQL 유형 3306을 선택 | 사용자 지정 TCP 3307로 수정 |
| 앱 아웃바운드 DB 대상이 앱 CIDR | DB CIDR 10.100.0.0/24와 10.100.1.0/24 |
| DB 응답 때문에 SG에 1024-65535 추가 | SG 응답 규칙 불필요. DB NACL은 별도 필요 |
| SG를 만들었는데 연결은 그대로 실패 | 실제 리소스의 SG 연결·경로·NACL 확인 |
| 최소 규칙을 추가했는데 전체가 열림 | 기본 전체 아웃바운드와 다른 연결 SG 확인 |
| Secret 읽기가 AccessDenied | IAM·KMS·Endpoint 정책 확인 |
시간 초과는 경로·방화벽을, 명시적인 AccessDenied는 권한을 우선 확인하는 단서입니다. 단서만으로 원인을 확정하지 않습니다.

# 콘솔 실습 C | DB·암호화·Secret 입력

## Aurora 생성 화면에서 놓치기 쉬운 칸
RDS → 데이터베이스 → 데이터베이스 생성 → 표준 생성. Aurora MySQL 호환 엔진과 요구 버전을 확인합니다. 설정 영역에서 클러스터 식별자 worldpay-rds, 인스턴스 구성에서 db.t3.medium을 선택합니다. 계정·리전에서 선택되지 않는 조합은 교사에게 차이를 기록합니다.
연결(Connectivity)에서 DB VPC, DB 서브넷 그룹, DB SG를 선택합니다. 퍼블릭 액세스 No, DB 포트 3307을 확인합니다. 추가 구성에서 암호화와 KMS 키를 확인하고 생성합니다. 완료 후 Writer endpoint를 기록하고 앞의 SQL 실습을 진행합니다.

## 고객 관리형 KMS 키
KMS → 고객 관리형 키(Customer managed keys) → 키 생성. 대칭(Symmetric), 암호화 및 복호화(Encrypt and decrypt) 용도를 선택합니다. 별칭은 학습용으로 식별하기 쉽게 정합니다. 키 관리자와 키 사용자를 구분하고 앱 역할이 복호화할 수 있는지 확인합니다. 키 별칭은 공식 고정값이 아닙니다.

## Secrets Manager에 접속정보 저장
1. Secrets Manager → 새 보안 암호 저장(Store a new secret).
2. 학습용으로 기타 보안 암호 유형(Other type of secret)을 선택하고 Key/value에 username, password, host를 입력합니다.
3. username은 app처럼 admin이 아닌 DB 사용자, password는 그 사용자의 비밀번호, host는 Writer endpoint입니다.
4. Encryption key에서 고객 관리형 키를 선택합니다. 이름은 worldpay-secret으로 지정합니다.
5. 이 과제에서 별도 순환 주기를 요구하지 않으므로 자동 순환을 임의로 필수 설정하지 않습니다. 검토 후 저장합니다.
6. 저장된 Secret 상세에서 이름과 암호화 키를 확인합니다. 학생 발표 화면에는 비밀번호를 펼치지 않습니다.

## PrivateLink 콘솔 확인
VPC → 엔드포인트 → 생성 → AWS 서비스 → secretsmanager 검색 → 서울 Interface 서비스 선택 → 앱 VPC와 앱 a/c 선택 → Private DNS 활성 → Endpoint SG 연결 → 생성. Endpoint SG 443의 소스는 App SG로 지정합니다.

# 콘솔 실습 D | ALB 규칙과 ASG 연결

![ALB 허용 규칙과 기본 403 처리](worksheets/images/worldpay-alb-rules.png)

## HTTP 리스너의 기본 응답 변경
EC2 → 로드 밸런서 → worldpay-alb → 리스너 및 규칙(Listeners and rules) → HTTP:80 선택 → 규칙 관리. 기본 규칙의 동작을 고정 응답(Return fixed response)으로 바꾸고 응답 코드 403을 저장합니다.
규칙 추가(Add rule)에서 경로 /v1/users와 HTTP 메서드 GET·POST 조건을 함께 지정하고 대상 그룹으로 전달합니다. /health와 GET 규칙을 따로 만듭니다. 우선순위는 중복 없이 지정합니다. 서로 다른 조건 종류는 AND, 같은 조건의 여러 값은 OR로 읽습니다.

## 시작 템플릿에서 ASG까지
시작 템플릿 생성 → AL2023 / t3.micro / App SG / 앱 IAM 프로파일 확인. Auto Scaling 그룹 생성 → worldpay-asg → 해당 템플릿·버전 → App a/c → 기존 로드 밸런서 대상 그룹 선택. 원하는 2 / 최소 2 / 최대 학습용 4, Name=worldpay-app 태그 전파를 설정합니다.
동적 조정 정책(Dynamic scaling policies)에서 대상 추적, 평균 CPU 사용률, 목표 70을 지정합니다. 생성 후 활동 기록(Activity)에서 실패 이유를 확인하고 대상 그룹에서 Healthy 상태를 확인합니다.

# 콘솔 실습 E | 로그·대시보드와 수업 진행

## 로그 그룹의 보존 기간
CloudWatch → 로그 → 로그 그룹 → 생성 → worldpay-log-group. 생성한 그룹의 보존 설정(Retention setting)에서 30일을 선택합니다. 앱 로그 수집 설정 후 로그 스트림을 열고, 최근 요청의 이벤트가 새로 들어오는지 확인합니다.

## 두 개의 대시보드 위젯
CloudWatch → 대시보드 → 생성 → worldpay-dashboard. 위젯 추가 → 지표 → ApplicationELB에서 본인 ALB의 HTTP_Fixed_Response_Count를 선택합니다. 통계는 학습용 Sum으로 지정합니다.
두 번째는 EC2 → AutoScalingGroupName 차원 → worldpay-asg의 CPUUtilization, 통계 Average입니다. 현재 인스턴스의 모니터링·지표 가용 여부를 확인합니다. 단일 InstanceId만 선택한 위젯과 구분합니다.

## 교사용 설명 순서
5분: 전체 구성도에서 입구·앱·DB 역할을 말하게 합니다.
10분: 라우팅 그림에서 목적지별 화살표를 학생이 고르게 합니다.
10분: NACL 그림의 요청·응답 포트를 빈 종이에 다시 쓰게 합니다.
15분: 콘솔에서 리소스 1개를 교사가 시연하고 학생이 동일한 설정을 확인합니다.
10분: ALB 그림에서 정상·비정상 요청을 분류한 뒤 자기점검표로 확인합니다. 시간은 수업용 예시입니다.

# 1단계 | VPC와 서브넷 만들기

## 콘솔 작업
1. 우측 상단 리전을 서울로 선택합니다. VPC → VPC 생성에서 VPC만 생성을 선택하고 두 VPC를 각각 만듭니다.
2. 앱 VPC에는 10.0.0.0/16, DB VPC에는 10.100.0.0/16을 지정합니다. Name 태그 철자를 확인합니다.
3. 두 VPC의 DNS 확인(DNS resolution)과 DNS 호스트 이름 설정을 확인합니다. 이후 피어링과 Private DNS를 사용합니다.
4. 서브넷 메뉴에서 아래 6개를 생성합니다. 이름 끝 a는 ap-northeast-2a, c는 ap-northeast-2c에 대응합니다.

## 공식 서브넷과 연결할 라우팅 테이블
- worldpay-pub-subnet-a: 10.0.0.0/24 / 앱 VPC / worldpay-pub-rt
- worldpay-pub-subnet-c: 10.0.1.0/24 / 앱 VPC / worldpay-pub-rt
- worldpay-app-subnet-a: 10.0.10.0/24 / 앱 VPC / worldpay-app-rt-a
- worldpay-app-subnet-c: 10.0.11.0/24 / 앱 VPC / worldpay-app-rt-c
- worldpay-db-subnet-a: 10.100.0.0/24 / DB VPC / worldpay-db-rt
- worldpay-db-subnet-c: 10.100.1.0/24 / DB VPC / worldpay-db-rt

## 확인 방법
각 서브넷의 상세 화면에서 VPC ID, IPv4 CIDR, 가용 영역을 확인합니다. 이름만 맞고 VPC가 틀린 경우 해당 VPC용 리소스에 연결할 수 없습니다. 라우팅 테이블은 생성 후 서브넷 연결을 명시적으로 설정합니다.

# 2단계 | 인터넷 경로와 VPC Peering

## Public와 App 경로
1. 인터넷 게이트웨이를 생성하여 앱 VPC에 연결합니다.
2. worldpay-pub-rt에 0.0.0.0/0 → 인터넷 게이트웨이 경로를 추가합니다. 공개 서브넷 두 개를 연결합니다.
3. Public 서브넷에 Elastic IP를 사용하는 공개 NAT Gateway를 생성합니다. Available 상태를 기다립니다.
4. 앱 라우팅 테이블 각각에 0.0.0.0/0 → NAT Gateway를 추가합니다. 학습용 고가용성 구성은 AZ별 NAT를 사용하는 방식입니다. NAT 수량은 공식 지문에 고정되어 있지 않습니다.

## Peering으로 앱과 DB 연결
1. VPC → 피어링 연결 생성: 이름 worldpay-vpc-peering, 요청자 앱 VPC, 수락자 DB VPC를 선택합니다.
2. 연결 요청을 수락하여 Active 상태로 만듭니다.
3. DNS 설정에서 양쪽의 원격 VPC DNS 확인을 활성화합니다.
4. worldpay-app-rt-a와 worldpay-app-rt-c에 10.100.0.0/16 → 피어링 연결을 추가합니다.
5. worldpay-db-rt에 10.0.0.0/16 → 피어링 연결을 추가합니다. DB 서브넷 두 개를 이 테이블에 연결합니다.

## 중요한 원리
피어링 연결만 만들면 패킷의 길이 생기지 않습니다. 양쪽 라우팅 테이블이 있어야 요청과 응답이 왕복합니다. DB 라우팅 테이블에는 0.0.0.0/0 인터넷 경로를 만들지 않습니다.
학습용으로 Bastion에서 DB 초기화를 한다면 Public 라우팅 테이블에도 DB CIDR의 피어링 경로가 필요합니다. 다만 DB NACL은 앱 서브넷만 허용하므로, 실제 DB 접속은 앱 EC2의 Session Manager에서 진행하는 편이 단순합니다.

# 보충 1 | 네트워크 경로를 한 줄씩 해석하기

## 라우팅 테이블은 목적지를 보고 길을 고릅니다
예를 들어 앱 EC2가 10.100.0.25의 DB에 접속한다고 생각해 봅시다. 앱 라우팅 테이블에는 10.0.0.0/16 local, 10.100.0.0/16 pcx-..., 0.0.0.0/0 nat-... 경로가 있습니다. 목적지와 가장 구체적으로 일치하는 10.100.0.0/16 경로를 사용하므로 DB 요청은 NAT가 아니라 Peering으로 갑니다.
반대로 앱이 인터넷의 패키지 서버에 연결하면 두 VPC CIDR에 속하지 않으므로 기본 경로 0.0.0.0/0의 NAT를 사용합니다. NAT는 앱의 외부 접속을 돕는 장치이며 DB 연결에 필요한 장치가 아닙니다.

## 서브넷 연결을 빠뜨리지 않는 방법
VPC → 라우팅 테이블 → 해당 테이블 선택 → 서브넷 연결 탭 → 서브넷 연결 편집에서 원하는 서브넷을 체크합니다. 경로 탭만 수정하고 서브넷 연결을 빠뜨리면 해당 서브넷은 다른 테이블의 영향을 받을 수 있습니다.
- worldpay-pub-rt: Public a/c 두 개 연결, 기본 경로 IGW
- worldpay-app-rt-a: App a 연결, 기본 경로 NAT, DB CIDR 경로 Peering
- worldpay-app-rt-c: App c 연결, 기본 경로 NAT, DB CIDR 경로 Peering
- worldpay-db-rt: DB a/c 두 개 연결, 앱 CIDR 경로 Peering, 기본 인터넷 경로 없음

## 콘솔에서 경로를 찾는 순서
1. EC2 상세에서 실제 서브넷 ID를 확인합니다.
2. 그 서브넷의 라우팅 테이블을 엽니다.
3. 목적지 IP가 어느 CIDR에 속하는지 판단합니다.
4. 선택되는 대상 NAT·IGW·Peering이 정상 상태인지 확인합니다.
5. 응답을 보내는 DB 쪽에서도 같은 과정을 반대로 확인합니다.

## 연습문제
앱 10.0.10.15 → DB 10.100.1.20: 선택 경로는? _______________
앱 10.0.11.15 → 인터넷: 선택 경로는? ______________________
DB → 앱 응답: DB 라우팅 테이블의 목적지 CIDR은? _____________
정답 확인: Peering / NAT / 10.0.0.0/16. 실제 연결 성공에는 SG와 NACL도 필요합니다.

# 3단계 | DB NACL과 보안 그룹

## 두 방화벽의 차이
보안 그룹은 리소스에 적용되며, 허용된 요청의 응답은 자동으로 허용합니다. NACL은 서브넷에 적용되며, 요청과 응답 방향을 각각 허용해야 합니다. NACL은 번호가 작은 규칙부터 적용합니다.

## DB NACL 구성 예시
VPC → 네트워크 ACL에서 worldpay-db-nacl을 DB VPC에 만듭니다. DB 서브넷 a/c에 연결합니다. 아래는 앱 EC2에서 DB로 접속할 때의 학습용 최소 예시입니다.
- 인바운드 100: TCP 3307 / 소스 10.0.10.0/24 / 허용
- 인바운드 110: TCP 3307 / 소스 10.0.11.0/24 / 허용
- 아웃바운드 100: TCP 1024-65535 / 목적지 10.0.10.0/24 / 허용
- 아웃바운드 110: TCP 1024-65535 / 목적지 10.0.11.0/24 / 허용
- 나머지 기본 * 규칙: 거부. 인터넷 0.0.0.0/0 허용 규칙을 넣지 않습니다.
임시 포트 범위는 클라이언트가 사용하는 응답 수신 포트를 포함해야 합니다. 앱이 시작한 연결의 DB 응답 목적지 포트는 3307이 아닙니다.

## 보안 그룹 구성 예시 (이름은 학습용)
- ALB SG: 인바운드 TCP 80을 사용자에게 허용 / 아웃바운드 앱 SG의 TCP 8080 허용
- App SG: 인바운드 TCP 8080을 ALB SG에서만 허용 / DB TCP 3307 및 엔드포인트 TCP 443 통신 허용
- DB SG: 인바운드 TCP 3307을 앱 서브넷 CIDR 두 개에서 허용 / DB를 인터넷 전체에 공개하지 않기
- Endpoint SG: 인바운드 TCP 443을 App SG에서 허용
문제에서는 보안 그룹의 80/443 아웃바운드를 전체 대상으로 허용할 수 있습니다. SSH를 사용한다면 Bastion 인바운드 22는 본인 접속 IP로 제한합니다.

# 보충 2 | NACL의 요청·응답을 그림처럼 따라가기

## 요청 패킷과 응답 패킷의 포트는 다릅니다
앱 IP를 10.0.10.15, DB IP를 10.100.0.25라고 가정합니다. 앱의 운영체제가 임시 포트 45000을 골라 연결하면 다음과 같이 이동합니다.
요청: 10.0.10.15:45000 → 10.100.0.25:3307
응답: 10.100.0.25:3307 → 10.0.10.15:45000
DB 서브넷의 인바운드 규칙은 요청의 목적지 3307을 허용합니다. 아웃바운드 규칙은 응답의 목적지 45000을 포함한 임시 포트 범위를 허용해야 합니다. 아웃바운드에 3307만 적으면 응답이 차단될 수 있습니다.

## 규칙 번호가 중요한 이유
NACL에 90번 전체 거부가 있고 100번 앱 허용이 있으면 먼저 만나는 90번에서 거부됩니다. 허용 규칙은 기본 * 거부 규칙보다 앞에 배치하고, 의도하지 않은 낮은 번호의 거부 규칙이 없는지 확인합니다.
NACL 생성 후에는 연결 대상을 반드시 DB 서브넷 두 개로 지정합니다. 앱 서브넷에 잘못 연결하면 패키지 설치와 HTTPS 통신까지 끊길 수 있습니다.

## DB SG와 NACL을 함께 확인
DB SG는 3307 요청의 출발지를 앱 CIDR로 제한합니다. SG는 상태를 기억하므로 허용된 연결의 응답을 위해 임시 포트 인바운드 규칙을 추가할 필요가 없습니다. NACL에는 요청·응답 규칙이 각각 필요합니다.
DB SG에는 앱 a만 허용하고 NACL에는 a/c를 모두 허용한 경우, 앱 c의 연결은 여전히 실패합니다. 두 방화벽 중 하나라도 거부하면 연결되지 않습니다.

## 실패 사례 설명하기

____________________________________________________________

# 4단계 | PrivateLink, Flow Logs, Bastion

## Secrets Manager를 내부 경로로 접근
1. VPC → 엔드포인트 생성에서 서비스 com.amazonaws.ap-northeast-2.secretsmanager를 선택합니다.
2. 유형은 Interface, VPC는 앱 VPC, 서브넷은 앱 a/c를 선택합니다. Private DNS를 활성화합니다.
3. Endpoint SG를 연결하고 앱 EC2에서 오는 HTTPS 443을 허용합니다. 엔드포인트 정책과 IAM 정책 모두 접근을 허용해야 합니다.
4. 앱 인스턴스에서 Secrets Manager 이름을 조회했을 때 엔드포인트의 비공개 IP로 해석되는지 확인합니다. NAT만으로 조회가 성공하는 상태와 구별합니다.

## VPC Flow Logs
두 VPC 각각의 Flow Logs 탭에서 로그를 활성화합니다. 학습용으로 CloudWatch Logs를 목적지로 선택하고 전달 역할과 로그 그룹을 준비합니다. 이 로그는 네트워크 트래픽 기록이며, 뒤에서 만드는 애플리케이션 로그 그룹과 역할이 다릅니다.

## 채점용 Bastion
EC2 → 인스턴스 시작: worldpay-bastion / Amazon Linux 2023 / t3.micro / worldpay-pub-subnet-a를 선택합니다. SSH를 쓴다면 공인 주소와 키를 준비하고, Session Manager라면 에이전트·IAM 역할·서비스 접속 경로를 준비합니다.
공식 지문은 Bastion에 Administrator에 준하는 권한을 요구합니다. 실습 전용 역할로 부여하고 검증 종료 후 회수합니다. 앱 인스턴스에는 관리자 권한을 그대로 복사하지 않습니다.

## 접속 후 확인 (Bastion 터미널)
```sh

aws configure set region ap-northeast-2

curl --version
```
Account가 자신의 실습 계정인지 확인합니다. 키를 파일에 직접 복사하기보다 인스턴스 역할을 사용합니다.

# 보충 3 | IAM 역할과 Secret 권한 예시

## 권한은 인스턴스에 역할로 전달합니다
IAM → 역할 생성에서 AWS 서비스 EC2를 신뢰하는 역할을 만듭니다. 이후 시작 템플릿의 고급 세부 정보에서 IAM 인스턴스 프로파일로 연결합니다. 정책을 만들기만 하고 템플릿에 역할을 연결하지 않으면 앱은 그 권한을 받지 못합니다.
아래는 Secret 읽기와 키 복호화만 보여주는 학습용 정책입니다. ACCOUNT_ID, SECRET_ARN, KEY_ID는 자신의 실제 값으로 바꿉니다. Secret ARN 끝에는 자동 생성된 접미사가 있으므로 콘솔의 전체 ARN을 복사합니다.
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "SECRET_ARN"
    },
    {
      "Effect": "Allow",
      "Action": "kms:Decrypt",
      "Resource": "arn:aws:kms:ap-northeast-2:ACCOUNT_ID:key/KEY_ID"
    }
  ]
}
```
이 예시에는 로그 전송과 Session Manager 권한은 포함하지 않았습니다. 사용할 기능에 맞춰 별도로 추가합니다. 또한 KMS 키 정책에서 앱 역할의 사용을 허용하는지도 확인해야 합니다. IAM에서 Allow여도 키 정책이나 엔드포인트 정책에서 차단하면 실패할 수 있습니다.

# 5단계 | Aurora MySQL과 테이블

## 콘솔에서 DB 생성
1. RDS → 데이터베이스 생성에서 Aurora MySQL 호환 엔진을 선택합니다. 공식 요구는 aurora-mysql8.0입니다.
2. 클러스터 식별자는 worldpay-rds, 인스턴스 클래스는 db.t3.medium, 포트는 3307로 지정합니다.
3. DB VPC와 DB 서브넷 a/c로 만든 DB 서브넷 그룹을 선택합니다. 퍼블릭 액세스는 비활성화하고 DB SG를 연결합니다.
4. 저장소 KMS 암호화를 활성화합니다. Secret 암호화에도 사용할 고객 관리형 KMS 키를 미리 준비할 수 있습니다.
5. 원문 요구 클래스·엔진 조합이 콘솔에서 선택되지 않으면 임의로 변경해 채점 통과라고 판단하지 말고, 사용 가능한 조합과 차이를 교사에게 기록해 확인받습니다.

## 앱용 DB 사용자와 스키마

```sh

```
```sql
CREATE DATABASE IF NOT EXISTS worldpay;

```
학습용 사용자 예: app. CREATE USER로 별도 계정을 만들고 worldpay.users에 SELECT, INSERT 등 실제 프로그램에 필요한 권한만 부여합니다. 앱 실행 안내에 추가 요구가 있으면 그 범위에서 조정합니다. app 계정으로 재접속해 조회와 INSERT가 가능한지 확인합니다.

# 보충 4 | DB 사용자 생성과 SQL 실습

## 관리자와 앱 계정을 분리합니다
관리자는 DB와 사용자를 만드는 초기 작업을 하고, 앱은 사용자 정보를 입력·조회하는 작업만 합니다. 아래는 학습용 app 계정의 예시입니다. 비밀번호 자리에는 본인만 아는 강한 값을 넣으며 학습지에 기록하지 않습니다.
```sql
CREATE DATABASE IF NOT EXISTS worldpay;
CREATE TABLE IF NOT EXISTS worldpay.users (
  uid INT AUTO_INCREMENT,
  name VARCHAR(255),
  age INT,
  PRIMARY KEY (uid)
);
CREATE USER 'app'@'%' IDENTIFIED BY '<본인만-아는-비밀번호>';
GRANT SELECT, INSERT ON worldpay.users TO 'app'@'%';
SHOW GRANTS FOR 'app'@'%';
```
계정이 이미 있으면 CREATE USER는 실패합니다. 중복 생성을 반복하기보다 기존 사용자와 권한을 확인합니다. '%'는 MySQL 계정의 호스트 패턴이며 인터넷 공개 설정을 의미하지 않습니다. 실제 접속 출발지는 네트워크와 DB SG로 앱 서브넷에 제한합니다.

## 앱 계정으로 재접속 후 확인
관리자 세션을 종료하고 app 계정으로 접속합니다. SELECT와 INSERT가 되는지 직접 확인합니다.
```sql
INSERT INTO worldpay.users (name, age)
VALUES ('sql-student', 26);
SELECT uid, name, age FROM worldpay.users
WHERE name = 'sql-student';
```
uid는 자동 증가하므로 1로 고정되지 않습니다. INSERT가 실패하면 SHOW GRANTS 결과, 실제 접속 사용자, DB·테이블 이름을 먼저 확인합니다. 프로그램에 추가 권한이 필요하면 그 이유를 확인한 범위에서만 확대합니다.

# 6단계 | Secret과 앱 실행 준비

## Secret 생성
Secrets Manager → 새 보안 암호 저장에서 worldpay-secret을 생성합니다. 고객 관리형 KMS 키(CMK)를 선택합니다. username은 admin을 사용하지 않습니다. host에는 DB의 Writer endpoint를 적습니다.
원문의 JSON은 username, password, host 예시이며 실제 내용과 다를 수 있다고 명시합니다. 실제 앱을 연결하는 확장 실습에서는 포트 3307과 DB worldpay를 어떻게 전달하는지 앱 설정을 확인합니다. port/dbname 같은 필드명을 추측해서 넣지 않습니다.

## 앱 인스턴스의 역할
- worldpay-secret에 대한 secretsmanager:GetSecretValue
- 해당 CMK에 대한 kms:Decrypt 및 키 정책 허용
- 앱 로그 전송에 필요한 CloudWatch Logs 권한
- Session Manager를 쓸 경우 해당 접속 권한과 통신 경로
정책의 Resource는 해당 Secret·키·로그 그룹 범위로 제한합니다. Secret 값과 키 권한 둘 중 하나라도 빠지면 읽기가 실패할 수 있습니다.

## 콘솔에서 앱 실행 환경 점검
1. EC2의 OS가 Amazon Linux 2023인지 확인합니다.
2. 앱 인스턴스 역할, Secret 이름, DB 포트·DB 이름을 점검합니다.
3. 시작 템플릿의 IAM 프로파일과 App SG 연결을 확인합니다.
4. 앱 연결을 확장 실습하는 경우 8080 리슨과 서비스 자동 시작을 확인합니다.
이 학습지는 인프라 설정 실습에 별도 바이너리 파일을 요구하지 않습니다. 공식 시험 응시는 실제 문제지의 배포 프로그램 관련 조건을 별도로 적용합니다.

## 실행 후 로컬 점검 (앱 EC2)
```sh
curl -i http://127.0.0.1:8080/health
```
정상 기대값: HTTP 성공 응답과 JSON {"status":"OK"}. 실패하면 서비스 로그 → Secret 접근 → DB DNS·3307 연결 → 스키마 순서로 점검합니다. 재부팅 후 자동 시작과 새 인스턴스에서도 동일하게 실행되는 구성을 준비합니다.

# 보충 5 | Secret·DNS·포트를 따로 확인하기

## 한 번에 앱 전체를 고치려 하지 않습니다
앱 실행 실패를 네 가지 질문으로 나눕니다. 이름을 IP로 찾을 수 있는가? 해당 포트에 연결할 수 있는가? 계정 인증이 되는가? 테이블을 읽을 수 있는가? 이 순서로 확인하면 네트워크 문제와 SQL 권한 문제를 구분하기 쉽습니다.

## 터미널에서 확인하는 예시
앱 EC2에 접속한 뒤 아래 값을 본인 DB endpoint로 바꿉니다. getent는 DNS 확인, mysql은 실제 DB 접속 확인입니다.
```sh
getent hosts <writer-endpoint>
mysql -h <writer-endpoint> -P 3307 -u app -p
```
- DNS 결과 없음: endpoint 오타, VPC DNS 설정, Peering DNS 설정을 확인합니다.
- 연결 시간 초과: 라우팅·SG·NACL을 확인합니다.
- Access denied: DB 계정과 비밀번호, 호스트 조건을 확인합니다.
- DB·테이블 없음: worldpay와 users 생성 여부를 확인합니다.

## Secret은 값 대신 메타데이터부터 확인
```sh
aws secretsmanager describe-secret   --secret-id worldpay-secret   --query '{Name:Name,KmsKeyId:KmsKeyId}'
```
이 명령은 이름과 암호화 키를 확인합니다. 성공하더라도 GetSecretValue와 kms:Decrypt가 모두 된다는 뜻은 아닙니다. 실제 값 읽기 권한은 앱 역할과 키 정책으로 추가 확인합니다. Secret 전체 JSON을 화면 캡처나 학습 결과에 남기지 않습니다.

## PrivateLink 확인
앱 EC2에서 secretsmanager.ap-northeast-2.amazonaws.com을 DNS 조회하고, 콘솔의 엔드포인트 네트워크 인터페이스 IP와 비교합니다. Private DNS가 꺼져 있으면 NAT 경로로 성공할 수 있으므로, 조회 성공만 보고 내부 경로 사용으로 판단하지 않습니다.

# 7단계 | ALB와 올바른 API만 전달하기

## 대상 그룹과 ALB
1. EC2 → 대상 그룹에서 인스턴스 대상, HTTP 8080, 앱 VPC를 선택합니다. 상태 검사 경로는 /health로 설정합니다.
2. 로드 밸런서 → Application Load Balancer를 생성합니다. 이름은 worldpay-alb, 인터넷 경계(Internet-facing), Public 서브넷 a/c를 선택합니다.
3. ALB SG를 연결하고 HTTP 80 리스너를 만듭니다. 리스너의 기본 작업은 고정 응답 403으로 설정합니다.

## 허용 경로의 리스너 규칙
학습용 예시로 아래 규칙만 대상 그룹으로 전달합니다. 숫자 우선순위는 중복되지 않게 정합니다.
- 규칙 10: 경로 /v1/users AND 메서드 GET 또는 POST → 앱 대상 그룹
- 규칙 20: 경로 /health AND 메서드 GET → 앱 대상 그룹
- 기본 규칙: 그 외 요청 → Fixed response / 상태 코드 403
/* 또는 /v1/*처럼 넓은 경로를 전달하면 구현하지 않은 API까지 앱에 도달할 수 있습니다. 쿼리 문자열 ?uid=3은 경로 조건 /v1/users와 별개입니다.

## 확인 방법
대상 그룹에 앱 인스턴스가 등록되어 Healthy가 되는지 확인합니다. 상태 검사 연결은 ALB에서 앱의 8080으로 들어가므로 보안 그룹도 동일한 포트를 허용해야 합니다.
브라우저에서 ALB DNS의 /health로 접속합니다. 루트 /는 공식 API 목록에 없으므로 403이어도 오류가 아닙니다.

# 8단계 | ASG와 새 인스턴스 자동 실행

## 시작 템플릿 준비
EC2 → 시작 템플릿에서 Amazon Linux 2023, x86 호환 이미지, t3.micro, App SG, 앱용 IAM 인스턴스 프로파일을 지정합니다. App 서브넷의 인스턴스에 공인 IP가 자동 부여되지 않도록 합니다.
앱을 연동하는 확장 실습에서는 AMI 또는 사용자 데이터에 앱 설치, 서비스 자동 시작, 로그 수집 설정을 포함합니다. 사용자 데이터에 DB 비밀번호를 직접 적지 않습니다. 설치 파일을 받는 경로가 NAT 또는 필요한 엔드포인트를 통해 접근 가능한지도 확인합니다.

## Auto Scaling Group 생성
1. 이름 worldpay-asg, 시작 템플릿과 명시적인 버전을 선택합니다.
2. 앱 VPC의 worldpay-app-subnet-a와 worldpay-app-subnet-c를 선택합니다.
3. 앞 단계의 ALB 대상 그룹을 연결합니다. 상태 검사 유예시간은 실제 초기 설치 시간을 고려합니다.
4. 최소 용량은 2 이상, 원하는 용량은 학습용 2, 최대 용량은 학습용 4로 설정합니다. 최대가 최소와 같으면 확장되지 않습니다.
5. 태그 Name=worldpay-app을 생성하고 새 인스턴스에 전파하도록 선택합니다.
6. 대상 추적 정책에서 ASG 평균 CPU 사용률 70%를 지정합니다.

## 중요한 확인
이미 실행 중인 한 대에서만 수동으로 프로그램을 켜면 새 인스턴스가 생성될 때 서비스가 실패합니다. 새 인스턴스가 사람이 접속하지 않아도 Secret을 읽고 앱·로그 수집을 시작하도록 해야 합니다.
학습용으로 원하는 용량을 일시적으로 3으로 올려 새 인스턴스의 자동 실행과 Healthy 전환을 확인할 수 있습니다. 이 검사는 CPU 70% 정책 자체의 부하 검증을 대신하지 않습니다. 확인 후 2로 복귀합니다.

# 9단계 | 애플리케이션 로그와 대시보드

## 애플리케이션 로그 수집
1. CloudWatch → 로그 그룹에서 worldpay-log-group을 만듭니다. 보존 기간은 30일로 설정합니다.
2. 원본 앱의 로그가 파일로 출력되는지 확인합니다. stdout만 있다면 서비스 설정으로 로그를 파일에 기록한 뒤 CloudWatch Agent가 읽게 하는 구성을 사용할 수 있습니다.
3. Agent의 수집 경로를 실제 로그 파일과 일치시키고 로그 그룹 이름을 worldpay-log-group으로 지정합니다. 인스턴스별 로그 스트림을 사용하면 구분하기 쉽습니다.
4. 앱 역할의 로그 전송 권한과 네트워크 경로를 확인합니다. Secrets Manager 엔드포인트가 있다고 CloudWatch Logs까지 자동 연결되는 것은 아닙니다.
5. API 요청을 한 번 보내고 5분 이내에 새 로그가 보이는지 확인합니다. Flow Logs가 보인다고 앱 로그 요구를 충족한 것은 아닙니다.

## 대시보드 생성
CloudWatch → 대시보드에서 worldpay-dashboard를 생성합니다. 두 위젯을 추가합니다.
- ALB: AWS/ApplicationELB의 HTTP_Fixed_Response_Count. 해당 worldpay-alb 차원, 통계 Sum을 사용한 예시로 잘못된 API 요청 건수를 봅니다.
- ASG: AWS/EC2의 CPUUtilization. AutoScalingGroupName=worldpay-asg 차원, 통계 Average를 사용해 그룹 평균 CPU를 봅니다.
ASG 차원의 지표를 사용하려면 인스턴스 모니터링 설정과 지표 가용 여부를 확인합니다. 단일 인스턴스 CPU만 표시하고 그룹 평균이라고 표시하지 않습니다.

## 실제 데이터로 확인
없는 API에 요청을 보낸 뒤 ALB 고정 응답 수가 증가하는지 봅니다. 지표 수집 시간 때문에 바로 보이지 않을 수 있으므로 시간 범위와 서울 리전, 대상 ALB/ASG를 함께 확인합니다.

# 보충 6 | 로그 수집 설정을 읽는 방법

## 로그 파일과 수집기를 연결합니다
학습용 로그 파일 경로를 /var/log/worldpay/app.log로 정했다고 가정합니다. 실제 앱 로그 경로가 다르면 아래 file_path도 바꿉니다. 빈 경로를 수집하도록 설정하면 에이전트가 정상이어도 앱 로그는 오지 않습니다.
CloudWatch Agent 설정의 핵심은 수집 파일, 로그 그룹, 로그 스트림입니다. 아래는 logs 부분의 학습용 예시입니다.
```json
{
  "logs": {
    "logs_collected": {
      "files": {
        "collect_list": [
          {
            "file_path": "/var/log/worldpay/app.log",
            "log_group_name": "worldpay-log-group",
            "log_stream_name": "{instance_id}"
          }
        ]
      }
    }
  }
}
```
로그 그룹 보존 기간 30일은 CloudWatch 콘솔에서 설정합니다. Agent 설정 파일을 저장한 것만으로 적용되지는 않으므로 에이전트의 설정 적용과 시작 상태를 확인합니다. 로그 파일을 읽을 권한, logs:CreateLogStream 및 logs:PutLogEvents 등의 전송 권한도 필요합니다.

## 검증은 실제 앱 요청으로 합니다
1. 앱 API에 요청하여 로그가 생성되는지 로컬 파일을 확인합니다.
2. CloudWatch의 서울 리전과 worldpay-log-group을 엽니다.
3. 요청을 처리한 인스턴스의 로그 스트림을 선택합니다.
4. 요청 시각과 새 로그의 시각을 비교해 5분 이내 도착을 확인합니다.
임의 테스트 문자열만 전송한 결과는 앱 로그 수집 성공의 증거와 구별합니다.

# 10단계 | API를 직접 검증하기

## Bastion에서 ALB 주소 설정
이 페이지는 앱이 실행 중인 환경에서 진행하는 확장 실습입니다. 콘솔 구성만 학습하는 경우 요청·응답 구조를 읽고 기대값을 적습니다. ALB DNS는 본인 리소스의 값으로 바꿉니다. 다음 요청은 실습 DB에 사용자 데이터를 생성합니다.
```sh
ALB_ENDPOINT='<본인-ALB-DNS>'
curl -i "http://$ALB_ENDPOINT/health"
curl -sS "http://$ALB_ENDPOINT/v1/users"   -H 'Content-Type: application/json'   -d '{"name":"student-test","age":26}'
```
POST 응답 예시는 {"uid":3}입니다. 숫자는 DB 상태에 따라 달라집니다. 응답에서 실제 uid를 확인한 후 아래 3을 받은 값으로 바꿉니다.
```sh
curl -i "http://$ALB_ENDPOINT/v1/users?uid=3"
curl -sS -o /dev/null -w '%{http_code}\n'   "http://$ALB_ENDPOINT/v1/users123"
```
조회 응답에는 생성한 이름과 나이가 있어야 합니다. 없는 API /v1/users123은 ALB의 고정 응답 403이어야 합니다.

## 공식 mark.sh 사용 전 읽기
제공된 스크립트는 검증 명령과 기대값을 출력하는 형태입니다. 출력 내용을 사람이 비교해야 하며, 스크립트 실행만으로 자동 합산된 최종 점수가 확정되는 것은 아닙니다. 원본에는 Secret 값을 출력하는 명령도 있으므로 전체 출력을 학생 제출물이나 공개 시트에 그대로 붙여넣지 않습니다. 비밀번호가 없는 점검 결과와 교사가 확정한 점수만 기록합니다.
공식 스크립트를 실행할 때는 Bastion 접속, awscli·curl, IAM 역할, 서울 리전을 먼저 확인합니다. 이 자료 제작 과정에서는 학생 AWS 계정에 실제 구축하거나 공식 스크립트를 실행하지 않았습니다.

# 보충 7 | ALB 응답을 표처럼 비교하기

## 정상 기대값을 먼저 정합니다
- GET /health: 실행 중인 앱의 상태 JSON을 반환합니다.
- POST /v1/users: JSON name·age를 전달하면 새 uid를 반환합니다.
- GET /v1/users?uid=<실제 uid>: 저장한 name·age를 반환합니다.
- GET /v1/users123: 앱으로 전달하지 않고 ALB에서 403을 반환합니다.
- GET /: 공식 API 목록에 없으므로 기본 403 동작을 확인할 수 있습니다.

## 상태 코드별로 어디를 확인하나요?
403: 요청이 허용한 경로·메서드인지 확인합니다. 정상 API까지 403이면 리스너 조건이나 우선순위를 확인합니다.
404: 앱이 없는 경로를 받은 것일 수 있습니다. 없는 API 시험에서 404라면 ALB가 너무 넓게 전달하고 있는지 봅니다.
502: 대상 프로세스나 응답 상태를 확인합니다. 앱이 중간에 종료되었는지와 대상 포트를 확인합니다.
503: 사용 가능한 정상 대상이 있는지, 대상 그룹이 올바르게 연결되었는지 확인합니다.
504: 앱 응답 지연, 앱에서 DB로 가는 연결, 방화벽과 경로를 확인합니다.
위 코드는 원인 후보를 좁히는 단서입니다. 상태 코드 하나만으로 원인을 확정하지 않습니다.

## 교차 검증하는 순서
1. 앱 EC2의 localhost:8080/health 확인
2. 대상 그룹 Healthy 확인
3. ALB /health 확인
4. 사용자 생성과 조회 확인
5. 없는 API 403 확인
6. 앱 로그와 ALB 고정 응답 지표 확인
앞 단계가 실패하면 다음 단계의 결과만 반복 확인하기보다 실패 지점부터 수정합니다.
