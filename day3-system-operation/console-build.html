STEP 0

시작 전 화면과 메모표

  1. 리전콘솔 오른쪽 위 → Asia Pacific (Seoul).
  2. CloudShell상단 검색창 오른쪽의 터미널 아이콘 → Open CloudShell.
  3. 확인aws sts get-caller-identity, aws configure set region ap-northeast-2.

아래 값은 만들 때마다 복사합니다: VPC ID, public/private subnet ID 4개, node security group ID, RDS endpoint, bucket name, Account ID, ACM certificate ARN, ALB DNS.

절대 기록 금지 DB password, access key, secret key는 문서나 GitHub에 저장하지 않습니다.

STEP 1 — VPC CONSOLE

VPC와 subnet 만들기

이동: 상단 검색창에 VPC → VPC dashboard → Create VPC → VPC and more

화면 필드입력
Name tagapdev
IPv4 CIDR10.0.0.0/16
Availability Zones2
Public subnets2
Private subnets2
NAT gateways1 per AZ 권장
VPC endpointsNone
DNS optionsEnable DNS hostnames/resolution 체크

Create VPC → 완료될 때까지 기다린 뒤 View VPC. Resource map에서 public subnet→IGW, private subnet→NAT 연결을 확인합니다.

subnet 태그

VPC → Subnets → public subnet 각각 선택 → Tags → Manage tags → kubernetes.io/role/elb = 1. private subnet에는 kubernetes.io/role/internal-elb = 1.

완료 화면: Your VPCs에 apdev 1개, Subnets에 apdev 관련 4개, NAT gateways가 Available.

STEP 2 — EC2 CONSOLE

보안 그룹 만들기

이동: EC2 → 왼쪽 Network & Security → Security Groups → Create security group

apdev-alb-sg

VPC=apdev. Inbound rules → HTTPS, TCP 443, source Anywhere-IPv4. HTTP 80은 HTTPS redirect가 필요할 때만 추가합니다.

apdev-rds-sg

VPC=apdev. 처음에는 inbound를 비워두고 생성합니다. EKS node group 생성 후 Edit inbound rules → MySQL/Aurora 3306 → Source=EKS node security group ID로 설정합니다.

완료 화면: RDS SG에 IP CIDR가 아니라 sg-...가 source로 보입니다.

STEP 3 — RDS CONSOLE

RDS MySQL 만들기

이동: RDS → Databases → Create database → Standard create

영역선택
EngineMySQL, version 8.0
AvailabilityMulti-AZ DB instance
Identifierapdev-rds-instance
CredentialsSelf managed, username appuser
Instance classBurstable → db.t3.micro
StorageGeneral Purpose SSD gp3, 최소 용량
Connectivityapdev VPC, private DB subnet group, Public access No
VPC SGChoose existing → apdev-rds-sg
Additional configurationInitial database name dev, port 3306

Create database. Databases 목록에서 Status=Available까지 기다립니다. DB 선택 → Connectivity & security → Endpoint를 복사합니다.

aws rds describe-db-instances --db-instance-identifier apdev-rds-instance \
 --query 'DBInstances[0].{Class:DBInstanceClass,MultiAZ:MultiAZ,Public:PubliclyAccessible,Endpoint:Endpoint.Address}' --output table

완료: db.t3.micro / MultiAZ true / Public false. Read replica가 없어야 합니다.

STEP 4 — S3 CONSOLE

이미지 bucket 만들기

이동: S3 → Buckets → Create bucket. Region=ap-northeast-2, 이름은 전 세계에서 유일한 값(예: apdev-images-ACCOUNT_ID). Object Ownership=ACLs disabled. Block all public access=체크 유지. Bucket Versioning=Enable.

Create bucket → bucket → Properties에서 region 확인 → Permissions에서 Block public access가 On인지 확인합니다. 정적 웹사이트 호스팅은 켜지 않습니다.

완료: S3 URL을 직접 공개하지 않아도 됩니다. product Pod가 IAM role로 읽고 동일 ALB의 /images/*에서 반환합니다.

STEP 5 — ECR + CLOUDSHELL

저장소와 이미지 3개

이동: Elastic Container Registry → Private registry → Repositories → Create repository. user, product, stress를 각각 생성하고 Scan on push를 켭니다.

ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
REGION=ap-northeast-2
aws ecr get-login-password --region $REGION | docker login --username AWS --password-stdin $ACCOUNT_ID.dkr.ecr.$REGION.amazonaws.com
for APP in user product stress; do
 docker build --platform linux/amd64 -t $APP:1.0 ./$APP
 docker tag $APP:1.0 $ACCOUNT_ID.dkr.ecr.$REGION.amazonaws.com/$APP:1.0
 docker push $ACCOUNT_ID.dkr.ecr.$REGION.amazonaws.com/$APP:1.0
done

완료 화면: 각 repository의 Images 탭에 tag 1.0, architecture amd64 이미지가 있습니다.

STEP 7 — EKS NODE GROUP

c5.large node 2대

이동: EKS → apdev-eks → Compute 탭 → Add node group

Name=apdev-c5, Node IAM role=EKS worker node role. AMI=Amazon Linux, Capacity type=On-Demand, Instance type는 c5.large만. Disk=gp3 30GiB. Desired/Minimum/Maximum=2/2/2. private subnet 2개를 선택하고 Create.

Status=Active 후 EC2 → Instances에서 EKS node 2대의 Instance type이 모두 c5.large인지 확인합니다. 이때 node SG ID를 복사하여 앞의 apdev-rds-sg 3306 source로 넣습니다.

aws eks update-kubeconfig --region ap-northeast-2 --name apdev-eks
kubectl get nodes -L node.kubernetes.io/instance-type,topology.kubernetes.io/zone

STEP 8 — CLOUDSHELL

DB 적재와 애플리케이션 배포

CloudShell에서 kubectl을 사용합니다. DB는 private이므로 mysql client 작업은 EKS 임시 Pod에서 합니다.

kubectl create namespace apdev
kubectl -n apdev run mysql-client --rm -it --restart=Never --image=mysql:8.0 --  mysql -h RDS_ENDPOINT -u appuser -p dev

연결되면 과제지 schema와 제공 load_user.dump를 적용합니다. 제공 데이터는 수정·삭제하지 않습니다.

kubectl -n apdev create secret generic mysql-secret  --from-literal=MYSQL_USER=appuser --from-literal=MYSQL_PASSWORD='PASSWORD'  --from-literal=MYSQL_HOST=RDS_ENDPOINT --from-literal=MYSQL_PORT=3306  --from-literal=MYSQL_DBNAME=dev
kubectl apply --dry-run=client -f k8s/
kubectl apply -f k8s/
kubectl -n apdev get deploy,pod,svc,endpoints
kubectl -n apdev logs deploy/user --tail=30

Service는 세 개 모두 ClusterIP입니다. ENDPOINTS가 none이면 Service selector와 Pod label을 맞춥니다. product에는 S3 최소 권한의 IRSA/Pod Identity service account를 연결합니다.

STEP 9 — CLOUDSHELL + EC2

Load Balancer Controller와 Ingress

AWS 공식 EKS 문서 순서로 controller IAM policy와 service account를 만든 뒤 Helm으로 설치합니다. 설치 후:

kubectl -n kube-system rollout status deploy/aws-load-balancer-controller
kubectl apply -f ingress.yaml
kubectl -n apdev describe ingress apdev
kubectl -n apdev get ingress -w

콘솔 이동: EC2 → Load Balancers. internet-facing Application Load Balancer 1개가 생성되고 Listener 443, target groups의 target이 Healthy여야 합니다. ALB가 없으면 controller log → IAM AccessDenied → subnet 태그 → Ingress Events 순서로 확인합니다.

STEP 10 — ACM / ROUTE 53

HTTPS AWS domain 연결

ACM: Certificate Manager → Request → Public certificate → 계정에서 사용할 AWS domain 입력 → DNS validation. Status=Issued까지 기다립니다.

Route 53: Hosted zones → 해당 zone → Create record → Alias On → Route traffic to Application Load Balancer → Seoul → apdev ALB 선택.

Ingress annotation의 certificate ARN을 ACM ARN으로 설정합니다. 채점 endpoint는 https://도메인만 제출하며 끝 슬래시와 경로를 붙이지 않습니다.

STEP 11 — WAF CONSOLE

비정상 403, 없는 API 404

WAF & Shield → Web ACLs → Create web ACL → Regional resources → apdev ALB 연결. Default action은 Allow. /v1/user, /v1/product, /v1/stress에서 허용하지 않은 method/형식만 Block하도록 규칙을 만듭니다.

Default Block을 사용하면 /v1/none도 403이 되므로 과제 요구와 어긋납니다. WAF → Web ACL → Sampled requests에서 어떤 규칙이 차단했는지 확인합니다.

curl -i https://AWS_DOMAIN/v1/user
curl -i https://AWS_DOMAIN/v1/none
# 첫 요청은 규격 위반이면 403, 두 번째는 404여야 함

STEP 12 — CLOUDWATCH

운영 화면 구성

CloudWatch → Metrics → All metrics → ApplicationELB에서 TargetResponseTime, Target 5XX, HealthyHostCount를 그래프로 추가합니다. RDS metrics에서 CPUUtilization, DatabaseConnections, FreeStorageSpace, ReadLatency, WriteLatency를 추가합니다.

CloudWatch → Alarms → Create alarm에서 ALB 5XX와 unhealthy host 알람을 설정합니다. EKS control plane log는 CloudWatch Logs의 /aws/eks/apdev-eks/cluster에서 확인합니다.
