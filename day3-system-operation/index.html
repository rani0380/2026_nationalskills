STOP — 제일 먼저 확인

한 번의 실수가 24점을 없앨 수 있습니다

Fargate · Lambda 금지

경기 시작 1시간 뒤 EC2 이외 컴퓨팅 자원이 하나라도 있으면 성능·비용 항목이 모두 0점입니다. EKS Auto Mode도 사용하지 않습니다.

DB는 지정 사양만

RDS MySQL 8.0, Multi-AZ DB instance, db.t3.micro, Primary 1대만 사용합니다. Read Replica와 추가 DB 금지.

노드는 c5.large

EKS 컨테이너 호스팅 노드는 EC2 c5.large만, 최소 수량으로 구성합니다. Spot은 중단 위험 때문에 피합니다.

서울 리전만

별도 언급이 없으면 모든 자원을 ap-northeast-2에 만듭니다. 사용하지 않는 EC2·VPC·다른 리전 자원도 감점 대상입니다.

# 작업 시작과 중간에 반드시 확인

aws sts get-caller-identity
aws configure get region

# 금지 컴퓨팅 자원 확인 (출력이 없어야 안전)
aws lambda list-functions --query 'Functions[].FunctionName'
aws ecs list-clusters --query 'clusterArns'
aws eks list-fargate-profiles --cluster-name apdev-eks

03 — Before you build

변수와 도구 준비

명령은 AWS CloudShell 또는 관리용 EC2에서 실행합니다. CloudShell은 명령 실행 환경일 뿐 애플리케이션 컴퓨팅 자원으로 사용하지 않습니다. 아래 대문자 값만 본인 환경에 맞게 바꿉니다.

export AWS_REGION=ap-northeast-2
export CLUSTER_NAME=apdev-eks
export DB_ID=apdev-rds-instance
export DB_NAME=dev
export DB_USER=appuser
export BUCKET_NAME=CHANGE-ME-UNIQUE-BUCKET
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)

# 설치 여부 확인
aws --version
kubectl version --client
eksctl version
helm version
docker --version
비밀번호를 Git에 올리지 마세요. DB 비밀번호는 Secrets Manager 또는 Kubernetes Secret에만 저장하고, 화면 캡처·쉘 기록·README에 남기지 않습니다.

04 — Network

VPC: 2개 AZ, public/private 분리

최소 권장 구조는 public subnet 2개(ALB), private subnet 2개(EKS 노드·RDS)입니다. 비용 최적화를 위해 NAT Gateway는 1개만 두는 선택지가 있지만 AZ 장애 시 외부 통신이 끊길 수 있습니다. 채점 트래픽 안정성을 우선하면 AZ별 NAT 2개가 유리하므로, 계정 비용 제한과 채점 비중을 보고 결정합니다.

  1. VPC10.0.0.0/16, DNS resolution/hostnames 활성화.
  2. Public subnetAZ a/c에 10.0.0.0/24, 10.0.1.0/24. Internet Gateway 경로 연결.
  3. Private subnetAZ a/c에 10.0.10.0/24, 10.0.11.0/24. NAT 경로 연결.
  4. 태그public: kubernetes.io/role/elb=1, private: kubernetes.io/role/internal-elb=1.
  5. 보안 그룹ALB 443→인터넷, RDS 3306→EKS node SG만 허용. DB public access는 No.
초보자 팁 직접 VPC를 만드는 과정이 익숙하지 않다면 eksctl이 생성하는 VPC를 사용하고, 만들어진 private subnet으로 RDS DB subnet group을 구성해도 됩니다. 불필요한 두 번째 VPC는 만들지 마세요.

RDS MySQL을 정확한 사양으로 만들기

# EKS 안에서 연결성만 확인
kubectl run mysql-check --rm -it --restart=Never \

06 — Object storage

S3: 공개하지 않고 애플리케이션으로 제공

aws s3api create-bucket \
  --bucket "$BUCKET_NAME" --region "$AWS_REGION" \
  --create-bucket-configuration LocationConstraint="$AWS_REGION"

aws s3api put-public-access-block --bucket "$BUCKET_NAME" \
  --public-access-block-configuration \
BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

aws s3api put-bucket-versioning --bucket "$BUCKET_NAME" \
  --versioning-configuration Status=Enabled

product 앱에만 s3:PutObject, s3:GetObject 권한을 부여합니다. 가장 좋은 방법은 EKS Pod Identity 또는 IRSA로 product 서비스 계정에 최소 권한 역할을 연결하는 것입니다. 액세스 키를 Secret에 직접 넣지 않습니다.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::CHANGE-ME-UNIQUE-BUCKET/*"
  }]
}

07 — Images

ECR에 3개 컨테이너 이미지 저장

for APP in user product stress; do
  aws ecr create-repository --repository-name "$APP" \
    --image-scanning-configuration scanOnPush=true 2>/dev/null || true
done

aws ecr get-login-password --region "$AWS_REGION" | \
  docker login --username AWS --password-stdin \
  "$ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com"

for APP in user product stress; do
  docker build --platform linux/amd64 -t "$APP:1.0" "./$APP"
  docker tag "$APP:1.0" "$ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com/$APP:1.0"
  docker push "$ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com/$APP:1.0"
done

제공 바이너리는 Amazon Linux 2023, x86_64, TCP/8080 기준입니다. Dockerfile은 바이너리를 복사하고 실행 권한을 준 뒤 8080을 노출하는 최소 이미지로 작성합니다.

FROM public.ecr.aws/amazonlinux/amazonlinux:2023-minimal
WORKDIR /app
COPY app /app/app
RUN chmod +x /app/app
EXPOSE 8080
USER 10001
ENTRYPOINT ["/app/app"]

08 — Kubernetes

EKS: EC2 c5.large만 사용

과제의 금지 조건 때문에 Fargate profile, EKS Auto Mode, Karpenter로 다른 타입을 자동 생성하는 구성을 사용하지 않습니다. 관리형 노드 그룹의 인스턴스 타입을 c5.large 하나로 고정합니다.

# 예시: 기존 VPC를 지정한다면 vpc.subnets를 함께 작성
cat > cluster.yaml <<'YAML'
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: apdev-eks
  region: ap-northeast-2
managedNodeGroups:
  - name: apdev-c5
    instanceType: c5.large
    desiredCapacity: 2
    minSize: 2
    maxSize: 2
    privateNetworking: true
    volumeType: gp3
    volumeSize: 30
    labels: { role: app }
YAML

eksctl create cluster -f cluster.yaml
aws eks update-kubeconfig --region ap-northeast-2 --name apdev-eks
kubectl get nodes -o wide
수량 판단 1대는 가장 저렴하지만 노드 장애·업데이트 때 서비스가 중단됩니다. 2대는 고가용성 점수에 유리한 현실적 최소안입니다. 노드가 정말 모두 c5.large인지 EC2 콘솔에서도 확인하세요.

09 — Workloads

세 애플리케이션 배포

DB 정보는 Secret, 일반 값은 ConfigMap으로 분리합니다. 모든 앱은 8080 포트, /healthcheck probe, stdout/stderr 로그를 사용합니다. user/product는 2 replicas, stress는 자원 상황을 보고 1~2 replicas로 시작합니다.

kubectl create namespace apdev
kubectl -n apdev create secret generic mysql-secret \
  --from-literal=MYSQL_USER='appuser' \
  --from-literal=MYSQL_PASSWORD='CHANGE-ME' \
  --from-literal=MYSQL_HOST='DB_ENDPOINT' \
  --from-literal=MYSQL_PORT='3306' \
  --from-literal=MYSQL_DBNAME='dev'

kubectl -n apdev create configmap app-config \
  --from-literal=S3_BUCKET="$BUCKET_NAME" \
  --from-literal=AWS_REGION='ap-northeast-2'
apiVersion: apps/v1
kind: Deployment
metadata: { name: user, namespace: apdev }
spec:
  replicas: 2
  selector: { matchLabels: { app: user } }
  template:
    metadata: { labels: { app: user } }
    spec:
      containers:
        - name: user
          image: ACCOUNT_ID.dkr.ecr.ap-northeast-2.amazonaws.com/user:1.0
          ports: [{ containerPort: 8080 }]
          envFrom: [{ secretRef: { name: mysql-secret } }]
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits: { cpu: 500m, memory: 512Mi }
          readinessProbe:
            httpGet: { path: /healthcheck, port: 8080 }
            initialDelaySeconds: 3
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /healthcheck, port: 8080 }
            initialDelaySeconds: 10
            periodSeconds: 10
---
apiVersion: v1
kind: Service
metadata: { name: user, namespace: apdev }
spec:
  selector: { app: user }
  ports: [{ port: 80, targetPort: 8080 }]

같은 패턴으로 product와 stress를 만듭니다. product에는 mysql-secret과 app-config, Pod IAM service account를 연결하고, stress에는 DB 환경변수를 넣지 않습니다.

kubectl apply -f k8s/
kubectl -n apdev get deploy,pod,svc
kubectl -n apdev logs deploy/user --tail=30
kubectl -n apdev logs deploy/product --tail=30
kubectl -n apdev logs deploy/stress --tail=30

10 — Edge

ALB 하나로 모든 경로 제공

  1. AWS Load Balancer Controller공식 절차로 설치하고 필요한 IAM 역할만 부여합니다.
  2. ACM계정에 존재하는 AWS 도메인에 인증서를 발급하고 DNS 검증합니다.
  3. Ingresspublic ALB, HTTPS 443, certificate ARN, health check를 설정합니다.
  4. WAF허용 method/path 형식을 벗어난 /v1/* 요청을 403으로 차단하도록 Web ACL을 ALB에 연결합니다.
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: apdev
  namespace: apdev
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS":443}]'
    alb.ingress.kubernetes.io/certificate-arn: ACM_CERTIFICATE_ARN
    alb.ingress.kubernetes.io/healthcheck-path: /healthcheck
spec:
  ingressClassName: alb
  rules:
    - host: AWS_DOMAIN_NAME
      http:
        paths:
          - path: /healthcheck
            pathType: Exact
            backend: { service: { name: user, port: { number: 80 } } }
          - path: /v1/user
            pathType: Prefix
            backend: { service: { name: user, port: { number: 80 } } }
          - path: /v1/product
            pathType: Prefix
            backend: { service: { name: product, port: { number: 80 } } }
          - path: /images
            pathType: Prefix
            backend: { service: { name: product, port: { number: 80 } } }
          - path: /v1/stress
            pathType: Prefix
            backend: { service: { name: stress, port: { number: 80 } } }
403과 404의 차이 존재하는 API 경로에 규격을 벗어난 요청은 WAF 규칙으로 403. 존재하지 않는 /v1/none 같은 경로는 앱 또는 Ingress 기본 backend에서 404가 되어야 합니다. WAF가 모든 미등록 경로까지 차단하면 404 채점이 실패합니다.

채점 플랫폼에는 반드시 https://AWS_DOMAIN_NAME만 입력합니다. 끝의 /나 /v1을 붙이지 않습니다. 외부 DNS나 개인 구매 도메인은 사용하지 않습니다.

11 — Operations

로그·지표·알람으로 운영하기

ALB

TargetResponseTime, HTTPCode_Target_5XX_Count, HealthyHostCount. Access log는 필요 시 S3에 저장.

EKS

Container Insights 또는 CloudWatch Observability add-on으로 CPU, memory, pod restart 확인.

RDS

CPUUtilization, DatabaseConnections, FreeStorageSpace, Read/WriteLatency 확인.

애플리케이션

requestid와 uuid로 stdout 로그를 추적. 비밀번호·요청 본문의 민감정보는 기록하지 않음.

알람은 ALB 5XX, target response time, unhealthy host, RDS CPU/connection 등에 설정합니다. 알람을 만드는 것보다 실제로 OK → ALARM → OK 전환과 대응 절차를 확인하는 것이 중요합니다.

12 — Verification

외부 클라이언트 기준으로 검증

채점의 응답시간과 코드는 클라이언트 도착 기준입니다. EKS 내부 curl만 성공했다고 끝내지 말고 인터넷에서 최종 HTTPS endpoint로 확인합니다.

BASE='https://AWS_DOMAIN_NAME'
RID='999999999999'
UUID='7c5a3c6a-758f-4bc5-9bdf-3e573a0ad729'

curl -sS -o /dev/null -w 'health %{http_code} %{time_total}s\n' "$BASE/healthcheck"

curl -sS -o /dev/null -w 'user POST %{http_code} %{time_total}s\n' \
  -H 'content-type: application/json' -X POST "$BASE/v1/user" \
  -d "{\"requestid\":\"$RID\",\"uuid\":\"$UUID\",\"username\":\"dbdump500001\",\"email\":\"dbdump500001@example.org\"}"

curl -sS -o /dev/null -w 'user GET %{http_code} %{time_total}s\n' \
  "$BASE/v1/user?email=dbdump500001@example.org&requestid=$RID&uuid=$UUID"

curl -sS -o /dev/null -w 'product GET %{http_code} %{time_total}s\n' \
  "$BASE/v1/product?id=dbdump50001&requestid=$RID&uuid=$UUID"

curl -sS -o /dev/null -w 'stress POST %{http_code} %{time_total}s\n' \
  -H 'content-type: application/json' -X POST "$BASE/v1/stress" \
  -d "{\"requestid\":\"$RID\",\"uuid\":\"$UUID\",\"length\":256}"

# 의도한 오류 코드 확인
curl -sS -o /dev/null -w 'bad user %{http_code}\n' "$BASE/v1/user"  # 규격 위반이면 403
curl -sS -o /dev/null -w 'none %{http_code}\n' "$BASE/v1/none"      # 404
부하 테스트 주의 과제 종료 시 진행 중인 모든 테스트를 중단해야 합니다. 실제 채점 트래픽 외에 큰 부하를 장시간 만들면 성능을 떨어뜨리고 비용을 증가시킵니다. 작은 단계로만 확인하세요.
